Environment Configuration milestone.

The problem we're solving

Right now your LoginPage knows this:

base_url = "https://www.saucedemo.com/"

Imagine tomorrow you have:

QA       → https://qa.example.com
STAGING  → https://staging.example.com
PROD     → https://example.com

We do not want:

if environment == "qa":
    ...
elif environment == "staging":
    ...

inside your page objects or tests.

The test should ideally remain:

login_page.navigate()
login_page.login(...)

while the framework determines which environment to use.

Your task — design first

Before I show you the implementation, answer these 3 questions:

Q1. Where should the environment-specific URLs live?

A. test_login.py
B. login_page.py
C. A dedicated configuration layer
D. Everywhere they're needed

Q2. How should the framework know whether we're running against qa or staging?

For example:

pytest --env=qa

What do you think should happen after pytest receives --env=qa?

Q3. If we later have 20 page objects, should each page object independently read the environment configuration, or should there be a centralized mechanism that provides configuration to them?

The key principle is:

Tests and Page Objects should not care where the application is running.

They should consume configuration.

Think of cls as:

A reference to the class itself.

So:

cls.environments

means essentially:

Config.environments

in this particular call.

It's not an object of the class — that's what self represents in an instance method.

Remember this distinction
self → current OBJECT / INSTANCE

cls  → current CLASS

For example:

class Config:

    environments = {...}

    @classmethod
    def get_environment(cls, environment):
        return cls.environments[environment]
Why this is useful in our framework

We don't need to create:

config = Config()

every time a page needs configuration.

We can centrally access:

Config.get_environment("qa")

That's the design reason we're using @classmethod here.
